# Memory 设计说明

[返回产品介绍](../README.md)

本文描述当前用户端的实现，不将设计目标视为已经验证的效果。主要代码位于 [memory-curator.ts](../server/domain/memories/memory-curator.ts)、[memory-service.ts](../server/domain/memories/memory-service.ts) 和 [server/index.ts](../server/index.ts)。

## 1. 存储什么

| 数据 | 用途 |
| --- | --- |
| 对话历史 | 保存用户与助手的原始交流，语音会话单独归类 |
| 知识文档及分块 | 保存和索引资料，为回答提供依据 |
| `memory_observations` | 等待提炼的观察，记录来源、内容摘要及处理状态 |
| `memories` | 提炼后的全局 / 项目长期记忆 |
| `memory_sources` | 记忆与观察的关联、来源标签及摘录 |
| `memory_reflections` | 观察处理时模型生成的整理说明 |
| `memories_fts` / `memory_vectors` | 全文检索与可选向量检索索引 |

记忆类型包括用户画像、偏好、工作方式、能力、项目事实、项目决策、技术约束、项目状态、经验和流程等。每条记忆还可保存置信度、重要性、证据次数、标签、生效 / 失效时间和替代关系。并非所有采集路径都会填写全部字段。

## 2. 信息如何进入记忆

四类主要来源：

1. **对话**：相关回答完成后，将用户陈述和助手回复记录为观察。提炼提示词要求不要将用户未确认的助手建议当成事实。
2. **文档**：扫描知识库后，文档内容进入观察链路，并根据项目关联路径确定范围。配置本地 Obsidian 仓库后，Markdown 变更会触发延迟重扫。
3. **项目行为**：读取尚未观察过的事件，例如任务变化，并附上对象当前信息。同类待处理行为可聚合，避免每次点击都生成一条记忆。
4. **用户介绍**：岗位、职责、沟通偏好、长期目标等自填信息可以作为观察来源。

采集受 `memory_auto_capture` 控制；文档和行为采集另有 `memory_document_capture`、`memory_behavior_capture` 设置。新库默认开启这些采集设置，但模型未配置或未开启时不会自动完成模型提炼。这些是底层设置，不代表当前界面已提供每一项独立开关。

观察通过内容哈希去重，并保存 `pending`、`processing`、`processed`、`failed` 等状态。采集原始观察与保存长期记忆是两个不同步骤。

## 3. 自动整理何时运行

当前本地服务的主要调度：

- 服务启动后约 5 秒尝试处理待办观察。
- 业务触发的学习请求通常经过约 1.2 秒防抖，再处理一批观察；主调度每批最多 30 条。
- 每 10 秒检查新的项目事件，有新观察时安排整理。
- 一批中有成功处理项时，约 5 秒后安排下一次处理。
- 处理队列可重新尝试 `failed` 项；没有成功项时，不会仅凭这一轮无限立即重试。后续触发或手动运行可再次处理。
- 另有手动整理接口，每次最多处理 100 条。

这是应用运行期间的后台工作，不是独立的云端定时服务。退出应用后，本机后台整理停止；上述时间是调度延迟，不是记忆必定完成的时限。网络和模型速度影响实际完成时间。

## 4. 如何新增、合并与替换

提炼时将观察、附近已有记忆和行为背景交给对话模型，要求返回结构化 JSON：

| 动作 | 实际行为 |
| --- | --- |
| `add` | 新建长期记忆，写入来源并建立索引 |
| `update` | 更新同一范围内的目标条目，增加证据和验证时间 |
| `supersede` | 新建条目并关联原记忆；符合条件的原条目标为已替代 |
| `skip` | 不保存该候选条目 |

新增前还会查找相似记忆。被判为可能重复且不是替代操作时，优先增加已有条目的证据，而非不断生成重复记录。模型提示词要求跳过寒暄、临时细节、未经证实的推测和不确定冲突。

**实现边界：** 当前自动提炼结果直接保存为 `confirmed`，这个状态不代表用户逐条确认过。`confidence`、`stability`、`autoApply` 等模型返回字段并未全部成为强制保存门槛；其中持久化路径没有依据 `autoApply` 或 `memory_auto_apply` 决定是否等待确认。不能把这些字段理解成已经实现的严格审批机制。

## 5. 周期复盘如何工作

观察成功处理后，系统检查近七天有处理活动的范围，为每个范围按日期创建至多一条复盘观察。复盘结合已有记忆与近期任务，要求模型整理重复信息、替代关系和有多次行为支持的工作方法。

复盘仍走同一个观察队列，并受行为采集设置影响。它不是每日固定时间触发的后台作业，也不自动清空旧记忆。`update` 原地修改正文；来源和替代关系可追溯，但不能据此宣称每次修改都具备完整版本回滚。

## 6. 后续回答如何使用记忆

项目问答主要组合两部分：

- **核心记忆快照**：从当前有效的全局与当前项目记忆中选择画像、偏好、工作方式、决策、技术约束等重要条目，默认最多 18 条。
- **相关记忆检索**：结合词法匹配、FTS5 / BM25，以及配置可用时的向量检索，按倒数排名融合；项目上下文通常取 8 条相关记忆。

检索会限制范围、状态和有效期。已替代、失效、拒绝或过期的记忆不作为当前有效规则；历史追溯场景可以另外读取旧记忆。命中记录更新访问次数和最近访问时间。

不同对话流程不完全一致：生活语音使用核心记忆与较轻的已确认记忆查找，不保证每轮执行向量检索。Embedding 配置不可用时，关键词 / 全文路径仍可工作。自动提炼本身需要可用的对话模型。

## 7. 如何查看和纠错

可在客户端记忆界面查看条目、范围和来源，编辑正文、类型、状态及有效期。底层还提供观察列表和学习状态接口，便于确认是尚未采集、等待处理，还是模型调用失败。

示例 API（由本机服务提供）：

- `GET /api/memories`：记忆列表。
- `GET /api/memories/:id/sources`：来源记录。
- `PATCH /api/memories/:id`：修改记忆。
- `GET /api/memory-learning/status`：学习队列状态。
- `GET /api/memory-learning/observations`：观察及错误信息。
- `POST /api/memory-learning/run`：手动尝试整理。

关闭采集不等于清空已有记忆，也不等于清除之前排队的观察。当前没有承诺自动遗忘、完整版本回滚或端到端隐私脱敏。

## 8. 费用与数据边界

长期记忆保存在本机 SQLite 中，但使用云端模型提炼时，观察内容、相关记忆及行为上下文会发给所配置的服务商；使用云端 Embedding 时，相关文本也会发送给该服务。后台整理是额外的模型请求，会产生相应延迟和费用。

记忆功能不会修改模型权重，不是微调。提示词要求不记录密钥，不等于代码已实现完备的敏感信息过滤。请勿将凭证放进聊天、技能正文或知识材料。模型仍可能误判，应检查重要偏好和关键项目决策是否被正确保存。
